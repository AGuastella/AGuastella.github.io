sonic

A 2015 laptop running 24/7 as a headless home server — operated like production, debugged from first principles.

linux systemd docker debugging ops

TL;DR: an old ASUS laptop with no out-of-band management, so every failure has to be prevented, detected, or recoverable remotely. Each problem below was root-caused, fixed with a script that backs up, verifies and prints its own rollback, and then confirmed across a real reboot.

The machine

An ASUS X555LJ on Debian 13, lid closed, no battery, powering on by itself when AC returns. System and service state live on a 500 GB SATA SSD; media lives on a 500 GB 5400 RPM laptop HDD. It runs, in Docker: Jellyfin (films and TV, with hardware transcoding), Navidrome (music), FileBrowser, and the database and review UI for Talia, whose jobs fire from systemd timers. Remote access is SSH over Tailscale, with tmux sessions that survive dropped links and handing off between phone and laptop.

Debugging stories

USB 3.0 stuck at USB 2.0 speed — a silicon bug, and a kernel trap

Every USB 3 drive trained SuperSpeed, enumerated cleanly at 5000 Mbps, then failed every SCSI command with DID_NO_CONNECT and silently re-attached on the USB 2.0 half at 480 Mbps (~40 MB/s). The transient connect/disconnect pair only shows in journalctl -k; after the fallback, sysfs makes it look like SuperSpeed never worked at all. Cause: the uas driver uses bulk streams on SuperSpeed links, and this Intel xHCI advertises 256 streams in a read-only capability register that don't actually work — so no BIOS update can fix it.

The usual advice, blacklist uas, made it worse: the device then enumerated perfectly and got no driver at all, with nothing logged. Reading usb-storage's storage_probe() explained why: it hands UAS-capable devices to uas whenever CONFIG_USB_UAS is enabled, without checking that the module is loaded. The working fix is the per-device US_FL_IGNORE_UAS quirk (quirks=VID:PID:u, baked into the initramfs), which keeps the device on bulk-only transport at full link speed: ~40 → ~320 MB/s, about 70% of the 5 Gbps theoretical ceiling — the practical limit for a protocol without command queuing.

One port still stuck at 480 Mbps after the fix. Over three rounds it looked like a USB 2.0-only port, a bad cable, and a cracked solder joint. It was dust on the SuperSpeed contacts, which sit behind the USB 2.0 pins — so the port still worked perfectly, just slowly. Lesson kept: 480 where you expect 5000 → clean the socket before suspecting anything else.

Containers started before their disk was mounted

After a reboot, media services showed "file not found" errors. The media disk is mounted with nofail (so a dead disk can't block boot), which also means nothing orders Docker after it: Docker came up at 13.5 s, the disk at 17.3 s, and containers had bind-mounted the empty directory underneath the mountpoint, on the SSD. Confirmed per process via /proc/<pid>/mountinfo device numbers. Fix: a RequiresMountsFor= drop-in on docker.service; verified on the next boot (disk at 7.0 s, Docker at 12.8 s, every container on the right device).

4K playback freezing with an idle CPU

The browser client can't play multichannel audio, so Jellyfin re-encoded only the audio — which still means rewriting the whole film as HLS segments. Those segments went to the same 5400 RPM disk the film was read from, and the head seeking between the two dropped throughput below the stream's bitrate. Measured: 4.5× more cumulative write latency than read latency on that disk, and an 18 GB segment cache that vanished when the player closed. Moving the transcode cache to the SSD and enabling throttling (which turned out to be ffmpeg -readrate 10, not pause/resume) took media-disk reads from 78 to 31 MB/s with zero writes, and playback smoothed out.

Fan control with a tachometer that goes dark

The laptop's EC stops reporting fan RPM (ENXIO) the moment PWM is switched to manual, so pwmconfig-style calibration is impossible and fancontrol's stall detection crashes the daemon. Calibrated start/stop thresholds by ear instead, and added a systemd safety net: Restart=always plus an ExecStopPost that hands the fan back to firmware control whenever the daemon isn't running — tested live during a real crash loop. Later, a threshold sitting inside the idle temperature band made the fan hunt on/off (fancontrol has no hysteresis); moving it clear of the band cut idle fan activity from 64% to 7% of samples over an hour of logging, while peaks under load stayed below the full-speed point.

Smaller ones

  • Head parking: the media HDD shipped with APM at its most aggressive setting and was parking its heads ~42 times an hour — on track to pass its rated load cycles within a year. APM 254, persisted via hdparm.conf: zero parks in the hours after, setting confirmed across a reboot.
  • "DNS unavailable" that wasn't an outage: the ISP hands out DNS servers inside 100.64.0.0/10, the CGNAT range Tailscale claims and firewalls on other interfaces, so their replies were dropped. Containers started in the few seconds before Tailscale rewrote resolv.conf kept the dead resolvers; Docker now gets fixed upstream DNS.
  • Scheduled tasks drifting into the day: Jellyfin's interval-based maintenance tasks anchor to server start time, so after a reboot a CPU-heavy audio analysis ran mid-afternoon. Pinned to fixed night-time triggers.

Operations

  • Three update lanes. There is no remote console, so anything that can cost access is never automatic. Security patches install unattended (no auto-reboot, and nothing that changes the boot path or remote access); everything else is monthly, at the keyboard, followed by a post-reboot check script; container images are pulled separately and deliberately. Gotcha found on the first dry run: APT config lists append, so Debian's default origins silently widened the "security-only" policy from 8 packages to 57 until cleared with #clear.
  • Alerting. Push notifications via ntfy on separate topics for the machine and for each service, so one can be muted without losing the other: a notice on every boot (which is how a power cut shows up), a 6-hourly check for full disks, Docker down, or failed units, and an OnFailure= template any new unit can opt into in one line. Tested against faked states before going live.
  • Post-reboot check. One script verifies everything a reboot can silently undo: kernel booted vs installed, the USB quirk in the initramfs, fan daemon and sensor numbering, disk mounted, containers healthy, Tailscale key expiry.
  • Change discipline. Every fix is a script that is dry-run by default or idempotent, takes a timestamped backup, verifies its own result, and prints its rollback. Root causes and the traps hit along the way are written down next to the scripts.
